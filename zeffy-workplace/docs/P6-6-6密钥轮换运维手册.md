# P6-6-6 · 密钥轮换与生命周期 · 运维操作手册

> 适用：Zeffy-WorkPlace 产物加密模块（`ARTIFACT_ENCRYPT_ENABLED`）的密钥运维。
> 依赖实现：`crypto_gate.py`（多版本密钥/DEK 重裹/三阶段回收/到期预警）+ `config.py` ENCRYPT_* 配置 + `/admin/governance/encryption/*` admin 接口 + `server/scripts/rotate_keys.py`（自动化脚本）。
> 安全原则：**密钥仅在内存态持有，绝不落日志/异常/接口输出**；所有变更操作必须 admin + 留痕。
> 本文件为仓库内正式版（与 `.trae/documents` 同名草案同步）。

---

## 0. 概念速览

| 术语 | 说明 |
|---|---|
| 当前版本 | `ENCRYPT_CIPHER_VERSION` 指向的活跃主密钥；新写入恒用它 |
| 历史版本 | `ENCRYPT_LEGACY_KEYFILES` 归档的主密钥；**仅解密**（代码级无加密接口） |
| 灰度版本 | `ENCRYPT_GRAY_MASTER_KEYFILES` + `ENCRYPT_ROTATE_GRAY_RATIO` 抽样写入的新密钥 |
| DEK 重裹 | 只解封旧 DEK → 用新主密钥重裹 → 重写密文信封；**不重加密明文**，块密文原样保留 |
| 密钥指纹 | 密钥文件内嵌 `fp=`（HKDF 派生 8B），加载时校验，损坏密钥拒载 |

**密钥文件格式**（`#zfk` 扩展头，兼容旧纯 32B 文件）：
```
#zfk ver=2 created=1770000000 fp=0123456789abcdef
<32B RAW 或 hex>
```

## 2. 常规轮换流程（v1 → v2）

### 阶段 A：准备新密钥
```bash
# 推荐用自动化脚本（§9）：生成双副本 + #zfk 头 + 0600
uv run python scripts/rotate_keys.py gen --out-dir /secure/keys --ver 2
# 手工方式：
openssl rand 32 | xxd -p -c 32 > /tmp/master_v2.hex
python - <<'EOF'
import os, hashlib
from cryptography.hazmat.primitives.kdf.hkdf import HKDF
from cryptography.hazmat.primitives import hashes
m = bytes.fromhex(open('/tmp/master_v2.hex').read().strip())
fp = HKDF(algorithm=hashes.SHA256(), length=8, salt=b'zfk-fp', info=b'fp').derive(m).hex()
import time
hdr = f"#zfk ver=2 created={int(time.time())} fp={fp}\n"
for p in ("/secure/keys/master_v2a.key", "/secure/keys/master_v2b.key"):
    with open(p, "wb") as f:
        f.write(hdr.encode() + m)
    os.chmod(p, 0o600)
print("written, fp=", fp)
EOF
```

### 阶段 B：灰度验证（推荐 ⭐）
```bash
# 1. 临时配置灰度：小流量（1%）用 v2 写，其余仍用 v1
ENCRYPT_CIPHER_VERSION=1            # 保持当前
ENCRYPT_GRAY_MASTER_KEYFILES=/secure/keys/master_v2a.key,/secure/keys/master_v2b.key
ENCRYPT_ROTATE_GRAY_RATIO=0.01
# 2. 重启服务使配置生效
# 3. 验证灰度写入的密文（v2 头）可正常 加/解/Range/断点续传/去重 全链路
#    观察 /admin/governance/encryption-status → lifecycle.gray_version=2
# 4. 确认无异常后进入全切；灰度比率可逐步 0.01 → 0.1 → 1.0（谨慎）
```

### 阶段 C：全量切换（官方轮换）
```bash
# 1. 新 v2 成为当前版本；旧 v1 移入归档（仅解密）
ENCRYPT_CIPHER_VERSION=2
ENCRYPT_MASTER_KEYFILES=/secure/keys/master_v2a.key,/secure/keys/master_v2b.key
ENCRYPT_LEGACY_KEYFILES=1:/secure/keys/master_v1a.key,/secure/keys/master_v1b.key
ENCRYPT_LEGACY_VERSIONS=1
ENCRYPT_GRAY_MASTER_KEYFILES=       # 清空灰度（全切）
ENCRYPT_ROTATE_GRAY_RATIO=0
# 2. 重启服务
# 3. 验证
#    a. 新写入 → cipher_version=2
#    b. 存量 v1 密文仍可读（归档密钥仅解密）
#    c. /encryption-status → lifecycle.legacy_versions=[1]
```

### 阶段 D：存量密文重裹（可选，建议做）
> 目标：把存量 v1 密文的 DEK 重裹到 v2，最终可回收 v1 密钥。**只重裹 DEK，不重加密数据**。

```bash
# 1. 先扫描版本引用，确定重裹范围（admin API 或本地脚本）
curl -H "Authorization: Bearer <admin_token>" \
  http://<host>/admin/governance/encryption/refs
#   返回 {"refs": {"1": N, "2": M}} → N 个 v1 密文待重裹

# 2a. 本地脚本分批重裹（推荐；进程内复用后端，见 §9）
uv run python scripts/rotate_keys.py rewrap --version 1 --batch 50 --dry-run   # 先预览
uv run python scripts/rotate_keys.py rewrap --version 1 --batch 50             # 执行

# 2b. 或按文件列表调 admin API（admin-only；必须显式 keys，禁无范围全量）
curl -X POST -H "Authorization: Bearer <admin_token>" \
  -H "Content-Type: application/json" \
  -d '{"keys": ["artifacts/task-a/doc.md", "artifacts/task-b/report.pdf"],
       "reason": "rotate v1->v2 rewrap"}' \
  http://<host>/admin/governance/encryption/rewrap
#   返回 {"rewrapped": N, "failed": M, "failed_keys": [...]}
#   失败项：重裹前先修复（多为密文损坏/密钥不可解），后单独重试

# 3. 重查引用，确认 v1 归零
curl -H "Authorization: Bearer <admin_token>" \
  http://<host>/admin/governance/encryption/refs
```

### 阶段 E：三阶段回收 v1
> 仅在 v1 引用归零后执行；物理删除在配置层由运维完成（本模块只做安全门槛与留痕）。

```bash
# 1. 阶段① 回收门槛校验（admin + reason 必填）
curl -X POST -H "Authorization: Bearer <admin_token>" \
  -H "Content-Type: application/json" \
  -d '{"version": 1, "reason": "v1 无活跃引用，进入回收"}' \
  http://<host>/admin/governance/encryption/recycle-key
#   ok=true → 零引用，可进入归档期；409 active_refs → 仍有 v1 密文，先重裹

# 2. 阶段② 归档保留 30 天：从 ENCRYPT_LEGACY_KEYFILES 移除 v1 条目
#    （若需回滚，30 天内可重新加入配置恢复解密）
ENCRYPT_LEGACY_KEYFILES=            # 移除 1:...
ENCRYPT_LEGACY_VERSIONS=            # 移除 1

# 3. 阶段③ 安全擦除（30 天后）：覆写式删除，不可恢复
shred -n 3 -z /secure/keys/master_v1a.key /secure/keys/master_v1b.key
rm -f /secure/keys/master_v1a.key /secure/keys/master_v1b.key
#    备份介质中的 v1 副本同步销毁
```

## 3. 到期预警处理

| 状态 | 剩余天数 | 建议动作 |
|---|---|---|
| warn | ≤30d | 安排轮换计划，准备新密钥 |
| high | ≤7d | 本周内完成轮换 |
| critical | ≤1d | **立即轮换**；若无法轮换，`ENCRYPT_KEY_CREATED_AT` 临时延后并评估风险 |

- 告警经治理通道：`/admin/governance/alerts` 可见 `type=encrypt, dim=encrypt-expiry`。
- 到期基准优先级：密钥文件内嵌 `created=` > 配置 `ENCRYPT_KEY_CREATED_AT` > mtime。**部署/复制/迁移会改 mtime，务必用内嵌或配置指定。**

## 5. 回滚

| 场景 | 回滚操作 |
|---|---|
| 轮换后发现 v2 异常 | 恢复 v1 为当前：`ENCRYPT_CIPHER_VERSION=1`、`ENCRYPT_MASTER_KEYFILES=v1 副本`、`ENCRYPT_LEGACY_KEYFILES=2:...`；v2 密文仍可读（归档仅解密） |
| 重裹误操作 | 重裹前备份的原密文恢复；或重新轮换回（重裹可逆，仅改信封） |
| 误回收 v1 | 30 天归档期内重新加入 `ENCRYPT_LEGACY_KEYFILES` 即可恢复解密；超期则无法恢复（须用备份介质） |
| 密钥文件损坏 | 用另一副本替换；副本全损则回退上一稳定版本配置 + 从备份恢复 |

> **回滚兜底**：`ARTIFACT_ENCRYPT_ENABLED=false` 立即停用加密，新写走明文；存量密文保留待恢复。

## 6. 故障排查

| 现象 | 可能原因 | 处置 |
|---|---|---|
| `key_loaded=false` + 告警 critical | 副本缺失/不一致/指纹不符/版本回退 | 检查 `ENCRYPT_MASTER_KEYFILES` 副本一致性；`#zfk ver=` 与 `ENCRYPT_CIPHER_VERSION` 是否匹配；`ENCRYPT_LEGACY_KEYFILES` 是否含 ≥ 当前版本（回退） |
| 旧密文解密失败「DEK 封套校验失败」 | 归档密钥未配置 / 头版本被篡改（AAD 绑定） | 确认 `ENCRYPT_LEGACY_KEYFILES` 含该版本；重裹过密文头版本已更新，无需再配旧版本 |
| 重裹失败清单非空 | 密文损坏/密钥不可解 | 单独读该 key 确认损坏；用备份恢复后重试重裹 |
| `recycle-key` 返回 409 active_refs | 仍有旧版本密文 | 先重裹至归零；`force=true` 仅应急（将永久丢失该版本解密能力，禁用推荐） |
| 到期时间异常 | mtime 被部署改动 | 用密钥文件内嵌 `created=` 或 `ENCRYPT_KEY_CREATED_AT` 指定 |

## 7. 安全红线速记

1. **旧密钥仅解密**：`_LegacyBundle` 无加密方法；切勿把旧版本配回 `ENCRYPT_MASTER_KEYFILES`。
2. **版本单调**：`ENCRYPT_CIPHER_VERSION` 只能增大，禁止回退（历史版本 ≥ 当前会拒载）。
3. **指纹校验**：密钥文件带 `fp=` 后，篡改即拒载；保持副本一致。
4. **重裹原子**：失败会跳过并留痕，不会破坏原文件；勿并发重裹同一文件。
5. **回收三阶段**：归档 30 天内可恢复，覆写擦除后不可恢复——**务必先确认引用归零**。
6. **权限**：`/encryption/*` 全部 admin-only，越权 404；普通用户无任何途径看到加密状态。

## 9. 自动化脚本（`server/scripts/rotate_keys.py`）

> 进程内复用 app 模块（与压测脚本同模式）；**不打印任何密钥内容**，仅元信息。
> 用法（在 server 目录，PYTHONPATH 指向 server 根）：

```bash
cd server
$env:PYTHONPATH="<repo>/server"     # Windows；Linux/macOS: export PYTHONPATH=<repo>/server

# ① 生成新主密钥（双副本 + #zfk 头 + 0600）
uv run python scripts/rotate_keys.py gen --out-dir /secure/keys --ver 2
#   可选 --created <epoch> 指定创建时间（默认 now）

# ② 加密健康/生命周期/引用分布 一览
uv run python scripts/rotate_keys.py status

# ③ 存量密文版本引用分布
uv run python scripts/rotate_keys.py scan

# ④ 把某版本密文 DEK 重裹到当前版本（分批；先 dry-run 预览）
uv run python scripts/rotate_keys.py rewrap --version 1 --batch 50 --dry-run
uv run python scripts/rotate_keys.py rewrap --version 1 --batch 50
#   输出：逐批 rewrapped/failed + 失败 key 清单；失败不影响原文件
```

### 9.1 脚本行为与安全约束
- `gen`：生成 `master_v{N}a.key` / `master_v{N}b.key`（双副本，均 0600），内嵌 `#zfk ver/created/fp`；指纹为 HKDF 派生 8B。
- `scan` / `status`：仅读密文头版本号与密钥元信息，**不加载密钥内容**；`status` 在加密关闭时显示 `enabled=False` 而非报错（兼容锚点）。
- `rewrap`：仅重裹 **dry-run 预览后显式确认的版本**；逐批调用 `crypto_gate.rotate_rewrap_deks`（进程内、原子、幂等、失败跳过 + 审计）。**不执行任何删除/回收**（三阶段回收须人工经 admin API）。
- 回收/擦除/灰度切换等**变更操作不在此脚本**（避免自动化误触密钥红线）；由人工按 §2 执行。

### 9.2 与 admin API 的配合
| 步骤 | 脚本 | 人工/admin API |
|---|---|---|
| 生成新密钥 | `gen` | — |
| 灰度/全切配置 | — | 改 .env + 重启（§2-B/C） |
| 引用扫描 | `scan` | `GET /admin/governance/encryption/refs` |
| 重裹 | `rewrap` | `POST /admin/governance/encryption/rewrap` |
| 回收门槛 | — | `POST /admin/governance/encryption/recycle-key` |
| 巡检 | `status` | `GET /admin/governance/encryption-status` |
