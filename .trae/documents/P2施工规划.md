> 🔧 **补强完成 2026-09-15（一致性 + lease 死任务检测二轮修复）**：`pytest` 全量 **89 passed / 1 skipped**；实机回归通过（审批收尾 done + lease 续约生效 `worker_id_touched=True`）：
> 1. **一致性巡检闭环**：`queued` 滞留需超 `QUEUED_STALE_SECONDS`（默认 60s）才重入队（避免与在途 job 竞争；job 丢失由该巡检兜底重投）；`attempts ≥ ARQ_MAX_TRIES` 仍滞留 → **死信**（节点/任务 failed + `dead_letter` 审计，终止无限重试）。
> 2. **lease 死任务检测闭环**：worker 经 `AgentRunner.lease_renewer` 钩子对**每个** active running 节点续约 lease（`repos.renew_node_lease`，仅 running 命中防脏写）——消除"任务级 job 后续节点无 lease"盲区；巡检回收两类死任务：**lease 显式过期**，或 **lease 缺失且 `updated_at` 超 grace（ARQ_JOB_TIMEOUT×1.5）**（兜住 worker 永久死亡无 lease 痕迹的节点）。HITL 等待节点仍不回收（留人工）。
> 3. 注：Core `update()` 同样触发列级 `onupdate`——状态/output/lease 写入自动续期 `updated_at`，与"最后活跃时间"语义一致；测试需显式 `values(updated_at=...)` 才不被覆盖。
>
> 🔧 **补强二完成 2026-09-15（HITL blocked 持久化 + 前端 DB 重建卡）**：`pytest` **89 passed / 1 skipped**；实机验证通过（审批挂起时验收节点 DB 持久化为 `blocked`，approve 后全 `done`，`/nodes` 返回 `node_type`）：
> 1. **HITL/人工 等待节点持久化为 `blocked`**（合法迁移 running→blocked）：审批挂起 = blocked 而非 running——重启后恢复白名单（仅 queued/running）天然跳过，不自动入队，留人工 resume；`run_resume` 审批通过时 blocked→running→done（`repos.set_node_status` 防并发夺走），驳回时 blocked→pending 重新排队走审批。
> 2. **前端据 DB 重建审批卡（P2-5 🔴）**：`NodeOut` 增 `node_type`（auto/human/hitl，`list_nodes_endpoint` 从模板填充）；前端 reconcile 拉取 `/tasks/{id}/nodes` 后，若发现 `status==='blocked' && node_type==='hitl'` 的节点即渲染审批卡——刷新/断线后不再依赖卡专用 WS 事件，据 DB 真相源重建。（注：当前单页 demo 无任务导航，故重建由 WS 携带 task_id 后触发 reconcile；追问走 answer 时节点保持 running，不置 blocked。）

P1 完成了自研工作流（状态机 + 乐观锁 + TaskNode 唯一真相源）与多 Agent 编排，但后台任务全部跑在 **in-process `TaskRunner`**（`asyncio.create_task` + 内存 dict），存在致命限定：**服务重启 / OOM / 崩溃时所有运行中、等待 HITL 的任务全部丢失，无持久化、无重试、无死信**。P1 文档已把此列为 P2 必须解决的风险。

P2 目标：
1. 任务**持久化**（入 Redis 队列 + DB 记录），服务重启不丢，运行中任务 **从 PG TaskNode 断点恢复**。
2. **先单 worker 持久化**（多 worker 并行 + Redis Pub/Sub 跨实例广播留 P3，用户已确认分期）。
3. **DAG 建模 + 串行执行**（`depends_on` 声明与校验，实际仍单活节点顺序跑，不真并行）。
4. **纳入前端**：处理 `agent_message / task_node_update / review_event`，渲染节点状态带 + 审批卡 + 追问卡。

强制约束（延续 P1）：**PG TaskNode 是唯一真相源，内存态不驱动业务**；保留乐观锁与 `AgentRunner.run / run_resume` 现有逻辑；克制、最小必要改动。

## 核心架构决策（已定）

| 决策 | 选择 | 理由 |
|---|---|---|
| 队列框架 | **ARQ**（独立 worker 进程） | async + 纯 Redis，与全异步代码契合；悲观执行天然实现"崩溃重跑" |
| worker↔API 关系 | **独立 ARQ worker 进程 + Redis Pub/Sub 单通道回传** | WS/前端在 API 进程；worker 里 emit 经 `zw:tasks` 通道单点回传 API 推 WS。此为一对一拓扑，**不是** P3 的多实例多对多广播，工作直接铺垫 P3 不浪费 |
| worker 启动兜底 | **DB rescan 重新入队**（`_job_id=task_id` 去重） | 兜住 in-flight job 从 Redis 流意外丢失的边缘情况 |
| DAG | **建模依赖 + 串行执行** | 保持"单活节点"不变式，`engine._activate_next` 只按依赖就绪挑节点，`AgentRunner` 完全复用，改动最小 |
| 断点恢复 | **ARQ 悲观执行 + DB rescan 双保险**；HITL 等待中任务天然靠人工 `user_decision` 重新入队 | 满足"重启不丢 + 待人工"语义 |

## 风险与回滚
- **R1 ARQ 冲击现有 async**：存量 `_submit` 闭包捕获 `ws` 需改写为入队；`AgentRunner/engine` 核心零改动。回滚=`git revert` P2 源码，`USE_QUEUE=false` 走回 P1 in-process（关入队开关即可）
- **R2 Redis 不可用**：入队抛错→`system_notify`；事件消费自愈重连；`/health` 加 Redis 探测；回滚同上
- **R3 重复执行（悲观执行重跑）**：`run()` 从 DB 重建幂等；fs 工具沿用"存在判断/临时+rename"幂等约定；`_job_id` + `attempts` 双层防重；接受"至少一次"为文档化语义（P3 加 lease 过期扫描）
- **R4 alembic 数据安全**：新增列均 nullable/带默认，autogenerate 产物人工逐行审后方可执行，不清 volume
