## 2. 分项设计

### 2.1 持久化断点（IndexedDB）—— 本批

**目标**：下载被中断后，刷新页面 / 换标签页 / 下次再下载同一产物时，从断点续传，不重复全量拉取。

**方案**：
- 引入一个轻量 IndexedDB 存储层 `lib/resume-db.ts`（无第三方库，<200 行）：
  - 表 `meta`（key=`{etag}_{rel}`，存 `etag/total/received/updatedAt`）与 `chunks`（`etag_{rel}_{seq}` → Blob）。
  - 写前先校验 `etag`：与当前 `HEAD` 强 ETag 一致才复用（沿用 P5-4 强指纹，**跨版本/文件变更强制清断点**）。
  - 版本字段 `DB_VERSION` 迁移预留；`maxSize` 沿用 `RANGE_MAX_SIZE` 熔断，超限直接全量。
- `fetchResumable` 增加 `persist?: boolean`（`downloadArtifact` 默认开）；先查残留断点 → 从已接收 `received` 续拉 → 完成/失败时更新。
- 失败保留已收字节与进度元数据；`FetchResumeError` 时写入断点，下次续传。

**风险**：IndexedDB 配额（Safari 私隐/配额限制）；多标签页并发写同一断点 → 用元数据乐观锁（比较 `etag` 一致才覆盖）。

**验收**：中断→刷新→续传成功，校验和与原文件一致；文件变更（ETag 变）→ 自动清断点从头；跨版本下载 → 不使用旧断点。

### 2.2 预览分页加载（大文本按页 Range）—— 本批

**目标**：承接流式首屏，大文本/日志可「继续加载下一页」按页 Range 累加，而非只显示开头 256KB。

**方案**：
- `ArtifactPreview` 增加「加载更多」：记录已读 `offset` + `etag`；每次按页 `fetchRangeSlice(offset, offset+PREVIEW_MAX_PREVIEW-1)` 累加；页间校验 ETag 一致（变了则提示重新打开）。
- 与 `truncateLines`（2000 行）叠加：行超限按"当前已加载"提示，不再一刀切"仅首屏"。
- 点击「加载更多」时才拉下一页，避免大文件默认整包进内存（保持 ⭐5 内存边界）。

**验收**：多页连续加载内容无缝隙/无重复；ETag 变更后停止并提示；内存不随文件无限增长。

### 2.3 速率限制 —— 本批

**目标**：下载/预览限速，避免弱网下大量并发挤占带宽，或配合限速做演示。

**方案**：`fetchResumable` 增加 `maxBytesPerSec`（`downloadArtifact` 传 `onProgress` 侧计算吞吐）；每个 chunk 后用 `await sleep(剩余时延)` 节流，使实际速率 ≈ 目标，且不阻塞事件循环太久（每块 ≤ 5s 控制）。

**验收**：限速后实际吞吐 ≤ 目标 ± 20%；取消/中断仍即时响应。

### 2.4 并行分块下载 —— 本批（突破串行 Ⓢ1，须谨慎）

**目标**：大文件并发拉取多块，缩短总耗时；**保留**正确性（ETag、长度、总量校验、重试）。

**方案**：
- 新增 `RANGE_MAX_CONCURRENCY`（前端 `range.ts` 常量 + 后端 config 预留，默认 1=纯串行兼容 P5-4）。
- `fetchResumable` 改为按并发度开 N 条独立 `fetchRange`（首块先行，块内仍串行重试）；用等长 `分片槽` + `received` 位图跟踪；块间 ETag 一致性共用初次 HEAD 的 etag。
- **不改变** 后端接口与幂等；`RANGE_MAX_SIZE`/熔断/降级路径不变。

**风险**：并发乱序拼接与完整性校验复杂度上升；单位置多块 → 需块级 `(start,end)` 记录，`.end` 对齐。
**验收**：并发 4 下载产物校验和与原文件一致；块错位/缺失触发重试；并发度=1 时与串行 P5-4 行为一致（回归锚点）。

### 2.5 多段 Range —— 记录为「明确不实现」

- 后端当前降级 200 全量是**安全合理**的行为；HTTP 客户端几乎不用多段 Range；如需实现会引入 `multipart/byteranges` 边界与缓存复杂度，收益远小于风险。
- **处置**：在设计文档标注「多段 Range 维持降级 200，不实现」，关闭该遗留项。

### 2.6 流式直写磁盘（File System Access API）—— 拆分/延后

- 依赖 `window.showSaveFilePicker` + `FileSystemWritableFileStream`，**仅 Chromium 系支持**；需为超大文件建立「不落内存 Blob」的独立流式下载通道（后端已有流式，前端需新增 WritableStream 消费），与现有内存续传路径并行。
- 收益集中在大文件保存，但浏览器覆盖有限 + 实现成本高。
- **处置**：记入遗留缺口，需要时单独立项（`downloadArtifact` 留 `streamToDisk?` 扩展位）。

### 2.7 上传断点续传 —— 单独立项

- 当前系统**无产物上传 API**；上传续传是「新增写入链路」（分片上传、合并、幂等、断点记录、配额），与现有下载/预览体系解耦，属于新子系统，远超本批「滞留项」性质。
- **处置**：不在本批；记入产品需求池，单独立项时按 P5 存储契约（三种幂等模式/原子写/校验和）设计上传接口。

## 3. 兼容锚点与回滚（本批 1/7/4/3）

- 所有改动**不触碰后端 Range 降级逻辑**；`RANGE_ENABLED=false` 时前端自动单次 fetch（零漂移锚点保持）。
- 持久化断点 `persist` 默认仅在 `downloadArtifact` 开启；预览首屏/单次 fetch 不受影响。
- 并行下载默认 `RANGE_MAX_CONCURRENCY=1`（回归 P5-4 串行行为）；可配置调高。
- 回滚：IndexedDB 断点可在设置中清理；删除 `persist`/并发配置即回退单次/串行。
